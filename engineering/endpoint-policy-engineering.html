Endpoint Application Control & Browser Hardening

Engineering policy controls while preserving compatibility with business applications.

Intune / Group Policy / AppLocker / CIS ChromeProfessional workstream
This case study describes the work and validation approach without disclosing internal policy names, tenant details, or user information.

Engineering problem

This work combined two practical problems: aligning browser settings with CIS guidance and explaining application blocks without weakening AppLocker controls. I also had to account for settings configured through both Group Policy and Intune.

Investigation and validation

  1. Mapped Chrome baseline requirements to existing Group Policy and Intune settings, checking for duplicate or conflicting configuration.
  2. Compared AppLocker enforcement events with publisher signatures, executable metadata, file versions, and hash-based exceptions to identify the specific rule involved.
  3. Documented policy backups, pilot checks, application exceptions, and rollback considerations before changing settings that could affect business-critical software.

Example: diagnosing an AppLocker block

I start with the AppLocker event, including the blocked path and rule collection. An event such as 8004 identifies a block, but the next question is whether a publisher rule, file hash, or packaged-app rule is appropriate. Checking the file signature and version first avoids adding a broad path exception that could allow unrelated executables.

Outcome

The resulting notes covered individual rule decisions, verification steps, browser policy overlap, and application compatibility. Pilot findings are distinguished from any broader deployment.
