Detection Triage & Evidence-Based Incident Investigation

Investigating identity and endpoint alerts through repeatable evidence collection and corroboration.

Microsoft Sentinel / Defender / KQLProfessional workstream
This case study describes the work and validation approach without disclosing internal policy names, tenant details, or user information.

Engineering problem

A sign-in from an unfamiliar location or a spike in failures is worth investigating, but neither is a complete incident narrative. I correlate the alert with sign-in details, related activity, and known administrative changes before deciding whether it needs escalation.

How I investigate

  1. Started with the affected identity, event timestamps, sign-in result, application, IP address, and related audit entries; used KQL to compare nearby events.
  2. Compared the telemetry with change windows, expected automation, previous sign-in patterns, or user confirmation, depending on the alert.
  3. Recorded what the evidence supported, what remained unknown, and why an alert was closed or escalated.

Example KQL starting point

This is a general starting query for reviewing recent Entra sign-ins, not a reproduction of an internal incident. The time window and user filter would be narrowed for the alert under investigation.

SigninLogs
| where TimeGenerated > ago(24h)
| project TimeGenerated, UserPrincipalName, IPAddress,
          AppDisplayName, ResultType, ConditionalAccessStatus
| order by TimeGenerated desc

Outcome

The work produced documented incident decisions across several Sentinel alert categories. I have not included incident counts or time-saving estimates because this case study does not contain verified aggregate reporting.
